# minimal-implementation

## 언제 사용하는가
새 기능·수정·리팩터링에서 코드를 **추가하기 전**. "이 정도는 그냥 짜자" 싶을 때일수록.

## 목표
요청된 문제를 푸는, 실제로 동작하는 **가장 작은 코드**. 추측성 기능 없이.

## 절차 (사다리 — 처음 걸리는 칸에서 멈춘다)
1. 이 코드가 꼭 있어야 하나? 추측성 요구면 건너뛰고 한 줄로 그 이유를 남긴다(YAGNI).
2. 이 저장소에 이미 있나? 헬퍼·유틸·타입·패턴을 grep으로 찾아 재사용. 몇 파일 옆의 것을 다시 짜는 게 가장 흔한 낭비다.
3. 표준 라이브러리로 되나? 되면 그걸로.
4. 언어/플랫폼 기본 기능으로 되나? (DB 제약 > 앱 코드, CSS > JS 등)
5. 이미 설치된 의존성으로 되나? 몇 줄로 될 일에 새 의존성 추가 금지.
6. 한 줄로 되나? 그럼 한 줄.
7. 그다음에야 동작하는 최소 코드.

## 검증
변경된 모든 줄이 요청과 직접 연결되는가? 비자명 로직(분기·루프·파서·돈/보안 경로)엔 실패하면 걸리는 실행 가능한 체크 하나를 남긴다.

## 하지 말아야 할 것
- 구현이 하나뿐인 인터페이스, 제품 하나짜리 팩토리, 안 바뀌는 값의 config.
- 인접 코드·주석·형식 "개선", 손대지 않은 것 리팩터링.
- 불가능한 시나리오용 방어 코드.
