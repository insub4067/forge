# systematic-debugging

## 언제 사용하는가
버그·테스트 실패·이상 동작을 만났을 때, **고치기 전에**.

## 목표
증상이 아니라 근본 원인을 찾아, 여러 호출부가 공유하는 **한 지점**에서 고친다.

## 절차
1. 재현한다 — 실패를 결정적으로 재현하는 최소 케이스나 명령을 먼저 확보. 재현 없이 추측 수정 금지.
2. 좁힌다 — 고치려는 함수의 **모든 호출부**를 grep으로 확인하고 실제 흐름을 끝까지 추적.
3. 근본 원인 — 여러 경로가 같은 함수를 지나면, 각 호출부가 아니라 공유 함수 한 곳에 가드를 넣는다(디프도 더 작다).
4. 고친다 — 최소 변경.
5. 증명 — 1의 재현 케이스를 다시 실행해 통과를 확인.

## 검증
재현하던 명령이 이제 exit 0(또는 통과)인가. 같은 함수를 쓰던 형제 호출부도 안 깨졌나.

## 하지 말아야 할 것
- 티켓이 짚은 경로만 패치하고 형제 호출부를 방치.
- 재현 전에 원인을 단정.
- 다른 에이전트의 진단을 검증 없이 그대로 수용.
