# change-impact-analysis

## 언제 사용하는가
기존 코드의 함수·타입·API·설정·데이터 구조를 수정하기 전. 특히 한 파일 수정이 다른 호출부나 테스트에 영향을 줄 수 있을 때.

## 목표
한 지점만 고치고 관련 호출부를 빠뜨리는 실수를 막는다. 수정 전에 영향 범위를 작게 확인하고, 필요한 곳만 함께 고친다.

## 절차
1. 변경 대상의 정의를 읽고 정확한 책임과 계약을 확인한다.
2. `grep`으로 직접 호출부·참조·import·설정 사용처를 찾는다.
3. 관련 테스트와 검증 경로를 찾는다. 테스트가 없다면 최소한 변경 계약을 깨는 결정적 체크를 정한다.
4. 영향 범위를 `필수 수정 / 검증만 필요 / 무관`으로 나눈다. 전수 리팩터링으로 확대하지 않는다.
5. 공유 원인이 있으면 호출부마다 패치하지 말고 가장 좁은 공통 지점에서 수정한다.
6. 변경 후 직접 영향받는 호출부와 기존 검증을 실행한다.

## 체크포인트
- 함수 시그니처를 바꾸면 모든 호출부를 확인했는가?
- 반환 타입·JSON schema·DB 필드를 바꾸면 생산자와 소비자를 모두 확인했는가?
- 공용 helper를 바꾸면 형제 호출부가 깨지지 않는가?
- 설정값이나 상태 이름을 바꾸면 오래된 문자열/enum 참조가 남지 않았는가?
- 변경 범위를 필요 이상으로 넓히지 않았는가?

## 검증
변경 전 찾은 직접 영향 경로가 모두 수정 또는 검증됐는지 다시 grep한다. 관련 테스트/build/checker가 통과해야 한다.

## 하지 말아야 할 것
- 티켓에 언급된 파일 하나만 보고 수정.
- 이름이 비슷하다는 이유로 관계없는 파일까지 리팩터링.
- 호출부 확인 없이 시그니처·schema·상태값 변경.
- 영향 범위 분석 자체를 긴 문서 작성으로 바꾸기. 탐색은 짧고 실행 가능한 근거 중심으로 한다.
