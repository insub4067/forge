# Evidence-Axis Expansion — 검증 축 확장

> 상태: Proposal (2026-08-25)
> 목표: "완료 = 검증 통과"의 **검증**을 test/build 통과 너머로 넓힌다. 오늘 나온 사고들은
> 전부 test는 통과하지만 다른 축(서버 생존·런타임 응답성·이음새)에서 깨진 것들이었다.

## 왜

FORGE의 완료 판정은 이미 여러 축을 본다: generic test/build, acceptance gate(요구사항),
integration(회귀), runtime smoke(self-repo UI 렌더). 그런데 2026-08-24~25 세션에서 나온
버그들은 이 축들을 **전부 통과하면서** 깨졌다.

| 버그 | test 통과? | 어느 축에서 깨졌나 |
|---|---|---|
| grep/list_dir 홈에서 폭주 → 서버 먹통 | ✓ (작은 입력) | 런타임 응답성(부하) |
| 이미지 경로 그대로 모델에 전달 | ✓ | 요청→모델 이음새 |
| 워크스페이스 유령 id | ✓ | 프론트 상태 이음새 |
| 압축 요약 run마다 유실 | ✓ | run 경계 이음새 |
| 모델 티어 전역 | ✓ | 세션별 상태 이음새 |

공통점: **단위 함수는 맞는데 이음새/부하/생존이 틀렸다.** test가 못 보는 축이다.

## 검증 축 (현재 → 확장)

```
현재:  test/build  ·  acceptance gate  ·  integration 회귀  ·  UI 렌더(self-repo)
확장:  + 서버 생존/응답성  + 이음새 프로브(핵심 경로)  + 인접 기능 회귀(부하 포함)
```

### 축 A — 서버 생존/응답성 (이번에 착수)

런타임 스모크가 정적 UI 렌더만 본다. 서버가 응답 불능이면 `page.goto`가 타임아웃 나
`unavailable`(검증 불가)로 처리 — **먹통이 "통과 못 함"이 아니라 "검증 안 함"으로 샌다.**
오늘 서버가 30분 먹통이었는데 이 축이 있었으면 self-edit이 그걸 verified로 넘기지 못했다.

- 스모크에 백엔드 응답성 확인을 추가한다: 페이지 로드 후 `/api/health`가 짧은 타임아웃
  안에 200인지. 안 되면 `unavailable`이 아니라 `failed`(=서버 생존 실패).
- 이벤트 루프 watchdog(구현됨, `slow_callback_duration=1.0`)이 로그에 범인을 남긴다.

### 축 B — 이음새 프로브 (구현됨, `probe.py`)

`backend/probe.py`가 라이브 서버 대상으로 핵심 경로 이음새를 검사한다(health·응답성·
모델 티어 세션별·이미지 인라인·[--full] 실제 세션). `test_probe_smoke.py`로 pytest에도
편입(서버 있으면 자동). 이 축을 self-repo 검증에 엮을지는 축 A 안정화 후 판단한다 —
probe는 **실행 중(옛 코드) 서버**를 치므로, 새 코드 검증과 라이브 검증의 경계를 명확히
해야 한다(백엔드는 재시작 없이 새 코드를 검증할 수 없다는 본질적 제약).

### 축 C — 인접 기능 회귀 (미착수)

"이 변경이 옆 기능을 안 깨뜨렸나"를 부하까지 포함해 본다. 지금은 repo test가 있을 때만
generic verify가 커버한다. 부하 회귀(작은 입력은 통과, 큰 입력은 폭주)는 test가 못 잡는다.
grep/list_dir 상한이 그 예다 — 예방은 어렵고, watchdog으로 **가시화**하는 게 현실적이다.
축 C를 위한 별도 부하 프로브는 speculative라 지금 만들지 않는다.

## 범위 밖 (이번에 안 함)

- 모든 도구/엔드포인트의 부하 프로파일링, formal 성능 회귀 게이트
- 별도 verification agent, 새 검증 DSL
- 임의 blocking을 정적으로 증명하려는 시도(비현실적)

원칙: 검증 축은 늘리되, 각 축은 **결정적이고 false-positive가 낮아야** 한다. 애매한 축은
`unavailable`로 정직하게 두고 통과로 승격하지 않는다.

## 이번 착수 (축 A만)

`_runtime_smoke`가 백엔드 응답성을 함께 검증하도록 최소 확장. 나머지 축은 데이터가
쌓인 뒤 판단한다.
