# Browser Use / Computer Use 도입 제안

> 상태: Proposal
> 작성 기준: 2026-08-23
> 북극성: **에이전트가 자기 UI를 스스로 열어보고 검증한다 — "build 통과"를 "실제로 뜨고 동작함"으로 승격.**
>
> **갱신 2026-08-23**: 1단계(런타임 스모크) 구현됨 — verify 게이트가 self-repo 빌드 후 Playwright로
> 앱을 headless 로드해 uncaught 예외·핵심 렌더를 검증한다(`_runtime_smoke`). 2·3단계(에이전트 도구화,
> 상호작용 검증)는 미구현.

## 1. 배경 — 왜 필요한가

FORGE는 코드 정확성엔 강하지만(결정적 build/test 게이트), **런타임·UI 검증엔 사각이 있다.** 실측 사례(2026-08-23):

- `showHidden` ref가 리팩토링 중 유실 → 워크스페이스 피커가 빈 목록. `npm run build`는 통과(런타임 에러라). 검증 게이트가 못 잡고 커밋됨.
- 예약 작업 모달의 입력칸이 빈 박스로 보임 — build 통과, 사람이 폰에서 발견.
- 컨텍스트 배너·대기큐 배지 등 실행 중에만 나타나는 요소는 idle 스모크로 확인 불가.

공통 원인: **verify가 "빌드가 되는가"만 보고 "실제로 렌더되고 동작하는가"는 안 본다.** 지금은 사람(또는 옆의 Claude Code)이 브라우저로 대신 확인한다. 이걸 하네스 안으로 들인다.

## 2. 결론 — Browser Use 먼저, 검증용으로 좁혀서

두 능력의 난이도·가치가 다르다.

| | Browser Use | Computer Use |
|---|---|---|
| 대상 | 웹 UI(FORGE 프론트, 로컬 서버) | 데스크톱 전체(마우스/키보드/화면) |
| 조작 근거 | DOM·접근성 트리·셀렉터(텍스트) | 좌표 + 화면 캡처 |
| 모델 요건 | flash로 충분(vision 불필요) | vision 필수(좌표 판독) |
| 결정적 검증 | 가능(콘솔 에러·셀렉터 존재·텍스트 일치) | 어려움(클릭 성공 여부를 프로세스로 확인 불가) |
| 안전 | 로컬 브라우저 한정 | 화면 전체 제어 — 되돌리기 어려움 |
| 규모 | 도구 5~6개, ~1일 | 안전장치 포함 며칠 |

**Browser Use가 지금 이득이 크고 철학에 맞다**(저가 모델 + 결정적 검증). Computer Use는 웹 범위를 넘는 네이티브 작업이 실제로 필요할 때까지 보류.

## 3. Browser Use 설계

### 3.1 기반
- **Playwright(헤드리스 Chromium)**. `SANDBOX_MODE=host`라 Mac에서 직접 구동 — 이미 프론트가 로컬 서버로 뜨므로 붙이기 쉽다.
- flash는 **픽셀이 아니라 DOM 텍스트/접근성 트리**로 조작한다. vision 없이 저렴. 필요 시 스크린샷을 기존 vision 모델로 넘긴다.

### 3.2 도구(안)
```
browser_open(url)            페이지 로드, 로드 완료까지 대기
browser_read(selector?)      DOM 텍스트 / 접근성 트리 반환(요소 위치 파악)
browser_click(selector)      셀렉터 클릭
browser_fill(selector, val)  입력
browser_console()            console 에러/경고 수집 ← 검증 핵심
browser_screenshot()         PNG(선택 — vision 필요할 때만)
```
좌표가 아니라 셀렉터 기반이라 결정적이고 재현 가능하다.

### 3.3 안전 경계
- 로컬(`localhost`) + 지정 허용 오리진만. 외부 임의 URL 탐색 금지(기본).
- 부수효과 도구(click/fill)는 기존 approval 게이트 재사용.
- 세션 종료 시 브라우저 컨텍스트 정리(리소스 누수 방지).

## 4. 단계적 도입 (우선순위 순)

### 1단계 — 런타임 스모크(에이전트 도구 아님, 검증 강화) · ~반나절
verify 게이트에 추가한다. build 통과 후:
1. 프론트 서버 기동 → `browser_open(localhost)`
2. `browser_console()` 에러 0 확인
3. 지정 셀렉터(헤더·composer 등 핵심 요소) 렌더 확인
→ 하나라도 실패면 `verification_failed`(커밋 금지). **오늘의 UI 사고 3건이 전부 여기서 잡힌다.** 안전(읽기 전용), 결정적, 저비용.

### 2단계 — 에이전트 도구로 노출 · ~1일
모델이 자기 변경을 브라우저로 열어보고 콘솔·렌더를 확인해 스스로 고치는 루프. 1단계 인프라 재사용.

### 3단계 — 상호작용 검증(선택)
클릭·입력 후 기대 상태를 셀렉터/텍스트로 단언하는 시나리오 테스트. E2E의 경량판.

## 5. Computer Use (보류)

기술적으로 가능하다: macOS `screencapture` + 좌표 클릭 도구 + vision 모델(좌표 판독). 실제로 Claude Code가 computer-use로 이 방식을 쓴다. 그러나 FORGE에는 지금 부적합하다.

- **철학 충돌**: 좌표 기반이라 vision 필수 → flash로 부정확, 비용↑. "저가 모델 + 결정적 검증"과 어긋난다.
- **결정적 검증 불가**: "클릭이 맞았는가"를 프로세스로 확인할 수 없다. LLM-as-judge를 게이트로 못 쓴다는 원칙과 충돌.
- **안전**: 화면 전체 제어는 bash 권한보다 위험하고 되돌리기 어렵다.
- **필요성 낮음**: FORGE UI가 웹 기반이라 Browser Use가 대부분을 커버한다.

→ FORGE 밖 네이티브 앱 조작이 실제 요구로 등장할 때 재평가. 그때도 별도 승인·격리 설계가 전제.

## 6. 비고용(non-goal)
- 외부 웹 자동화·스크래핑(제품 범위 아님)
- 픽셀 기반 vision 조작을 기본 경로로 삼기(셀렉터 우선)
- Computer Use를 이번 범위에 포함

## 7. 완료 기준(1단계)
- verify에 런타임 스모크 추가, `showHidden` 유형 회귀를 재현 테스트로 확인
- 콘솔 에러/셀렉터 누락 시 `verification_failed`로 커밋 차단
- Playwright 의존성·기동을 host 모드에서 재현 가능하게 문서화
